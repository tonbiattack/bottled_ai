## はじめに

ゲームを自動操作するボットでは、「判断が弱い」と「そもそも判断結果がゲームに届いていない」を明確に分ける必要がある。Slay the Spire 用の Bottled AI を Windows 環境で起動し、Ironclad と Silent の戦略を試した記録には、戦闘ロジック以外にも重要な障害が残っていた。

この記事では、`tonbiattack/bottled_ai` の 2026-08-25 のコミットと実行記録をもとに、外部プロセス型ゲームボットで発生した四つの層の問題を整理する。結論は単純である。**ゲームAIの品質を測る前に、起動設定、ロケール、通信エラーの表現、テストの再現性を観測可能にしなければならない。**

> 対象は Communication Mod がゲームと Python プロセスを標準入出力で接続する構成である。本記事は特定の Windows 環境で確認した記録を一般化しすぎないよう注意し、設定値そのものではなく切り分けの方法を共有する。

## 全体像: 失敗は「AI」ではなく通信経路のどこでも起こる

ボットの一手がゲームに反映されるまでには、少なくとも次の経路がある。

```text
ゲーム起動
  └─ ModTheSpire / Communication Mod の設定読込
       └─ 外部 Python プロセスを生成
            └─ ゲーム状態を JSON で送る
                 └─ Python が状態を解釈してコマンドを返す
                      └─ Communication Mod がコマンドを検証し、ゲームへ適用
```

このどこかで止まると、画面上は「ボットが動かない」または「急に止まった」に見える。しかし、原因も対処も異なる。本件のコミット記録からは、次の四層を分けられる。[1]

| 層 | 実際に起きた事象 | 表面上の症状 | 本当の原因 |
| --- | --- | --- | --- |
| 起動設定 | `command` が空の設定を読んでいた | 外部プロセスを開始できない | 設定ファイルの配置先が違った |
| ロケール | 日本語表示のカード名が文字化けした | コマンドが無効として拒否される | 名前ベースの境界で文字コード・ロケールに依存した |
| プロトコル | エラーJSONを通常のゲーム状態のように扱った | `KeyError` など二次エラーで止まる | エラー応答を型として区別していなかった |
| 検証環境 | `ai` パッケージの解決が曖昧 | 通常の pytest 実行が失敗する | テスト用と本体用の名前空間が衝突した |

## 1. 起動設定: 設定値より「誰がどのファイルを読むか」を確認する

最初の症状は、ゲーム内の **Start external process** を何度実行してもボットが開始せず、ゲームログに次だけが出るものだった。

```text
ERROR communicationmod.CommunicationMod> Could not start external process.
```

このとき `communication_mod_errors.log` は空で、ボット側の `logs/` にも起動ログがなかった。重要なのは、Python の構文やボットの意思決定を疑う前に、**Python プロセスが一度でも生成されたか**を確認したことである。[1]

調査の結果、起動コマンドは `%LOCALAPPDATA%\ModTheSpire\config.properties` に書かれていた一方、Communication Mod が読むのは `%LOCALAPPDATA%\ModTheSpire\CommunicationMod\config.properties` だった。後者にある `command` は空だったため、Java 側が `ProcessBuilder` を作る段階で失敗しており、Python は起動前だった。[1]

| 確認項目 | 失敗時の観測 | 解釈 |
| --- | --- | --- |
| Mod の読み込み | BaseMod、StSLib、Communication Mod の初期化完了 | Mod の未導入・未読込ではない |
| Python 側ログ | 生成されない | Python 到達前の失敗を示す |
| `communication_mod_errors.log` | 0バイト | 子プロセスの標準エラーではない可能性が高い |
| Mod 固有の設定ファイル | `command=` が空 | 外部プロセス生成失敗の直接原因 |

ここから得られる教訓は、設定ファイルを編集するときに「アプリケーション名に見える親ディレクトリ」ではなく、**実装が名前空間として指定する設定パス**を確認することである。外部プロセスを使う統合では、設定値が正しくても、読まれる場所が間違っていれば何も始まらない。

修正後は、Communication Mod のログに `Received message from external process: ready` が出ること、子プロセスが継続していること、ボットの `default.log` に起動とゲーム状態の記録があることを成功条件にした。[1] 「メニューを押してもエラーが出ない」だけではなく、**プロセス生成・ハンドシェイク・双方向通信**の三点を分けて確認すると、次の障害も切り分けやすい。

## 2. ロケール: 表示名をプロトコルの識別子にしない

起動後には別の失敗があった。ゲーム表示が日本語の環境では、Communication Mod から Python に渡されるカード名が文字化けすることがあり、その名前を `choose` コマンドへ戻すと「無効な引数」として拒否された。[1]

この問題は単なる表示崩れではない。カード名が次の二つの役割を兼ねていたことが本質である。

1. 人間が画面で読むための**ローカライズ済み表示名**。
2. プログラムが対象を選び、外部プロトコルへ返すための**識別子**。

表示名はロケールや文字コードの影響を受ける。識別子は影響を受けてはいけない。この二つを同じ文字列にすると、UI言語の変更だけで自動化プロトコルが壊れる。

| 設計 | ロケール変更への強さ | デバッグのしやすさ | 推奨 |
| --- | --- | --- | --- |
| 表示名で内部判定し、表示名をそのまま送る | 弱い | 画面との対応は分かりやすいが、文字化けに弱い | 避ける |
| 安定した内部IDで判定・送信し、表示名はログ専用にする | 強い | ログに ID と表示名を併記できる | 推奨 |
| ロケールを英語に固定する | 当面は安定する | 導入が早い | 回避策としては有効 |

この環境ではゲーム設定の `LANGUAGE` を `ENG` に変更し、英語のカード名で通信することで回避した。[1] これは運用上は合理的だが、恒久策ではない。恒久策は、通信で `card_id`、`uuid`、手札インデックスなどの安定した値を使い、表示名を人間向けの注釈に限定することである。

## 3. プロトコル: エラー応答を通常状態としてパースしない

文字化けしたコマンドが拒否されると、Communication Mod はエラー応答を返す。ところが、修正前の Python 側はそのJSONを通常のゲーム状態に近いものとして扱い、必要なキーがない場所で `KeyError` になっていた。これでは「コマンドが無効だった」という一次原因が、「キーがない」という二次エラーに隠れてしまう。

コミット `2f1152d` では、`GameState` の初期化時に `error` キーを先に検査し、見つかった場合は `RuntimeError("Communication Mod rejected command: ...")` を送出するよう修正した。さらに、無効引数のメッセージが例外に残ることをテストしている。[2]

```python
# 実装の要旨
if "error" in json_state:
    raise RuntimeError(
        "Communication Mod rejected command: " + json_state["error"]
    )
```

これは小さな変更だが、外部連携の信頼性には大きい。プロトコル上の応答は少なくとも次の型に分けるべきである。

| 応答型 | 必須フィールドの例 | アプリケーションの扱い |
| --- | --- | --- |
| 正常なゲーム状態 | `game_state`、進行状態、選択肢 | 通常の意思決定へ渡す |
| コマンド拒否 | `error`、拒否理由 | 行動と状態スナップショットを記録して停止または再試行する |
| 初期接続・準備完了 | `ready_for_command` など | ハンドシェイクとして処理する |
| 不明な形式 | 型情報、元JSON | プロトコル不整合として明示的に失敗させる |

失敗メッセージを残すだけでなく、送信したコマンド、ゲームのロケール、カードの内部IDと表示名、直前の状態ハッシュも同じログイベントに入れると、文字化け・戦略バグ・通信断を区別できる。

## 4. 検証: テストが通ることとゲームで動くことは別の契約である

実行記録では、単体テストに `PYTHONPATH="$repo/tests;$repo"` のような設定が必要だった。通常の `python -m pytest` では、テスト側と本体側の `ai` パッケージのどちらを解決するかが曖昧になり、フィクスチャの import に失敗するためである。[1]

これはゲーム中の戦闘ロジックとは別問題だが、再現性に直結する。テストを「全員が同じコマンドで実行できる」状態にしなければ、戦略比較の前提が揺らぐ。今回の分析環境では、明示的な `PYTHONPATH` を使って現行テストを実行し、**1158 passed, 1 skipped** を確認した。しかし、この合格は固定された局面の期待コマンドを保っていることを示すだけで、実際のゲームプロセスとの通信や戦略全体の勝率を証明するものではない。

| テスト層 | 現在確認できること | 追加すべきこと |
| --- | --- | --- |
| Python構文・単体テスト | 状態変換や特定局面のコマンド | 一般的なロジック退行の防止 |
| 通信プロトコルテスト | `error` JSON が理由付き例外になる | 正常・拒否・未知形式の型分岐 |
| ロケール統合テスト | 現状は英語設定での回避 | 英日など複数ロケールで ID が不変であること |
| ゲーム統合テスト | `ready` と状態応答の確認 | 実ゲームでのコマンド適用・再起動・タイムアウト |
| 戦略ベンチマーク | 単発試行の所感 | 同一 seed 群での勝率、到達Act、戦闘ターン数、被ダメージ |

また、`main.py` で Ironclad 用 `REQUESTED_STRIKE` から Silent 用 `SHIVS_AND_GIGGLES` へ切り替えたコミットは、戦略選択の設定変更であり、共通比較器やシミュレータを変更したものではない。[3] [4] そのため、キャラクターを変えて挙動を比較することは探索的には有益でも、共通戦闘ロジックの改善を検証する実験にはならない。戦略変更・評価器変更・環境変更を同じ実験で混ぜず、seed とバージョンを固定して一つずつ比較するべきである。

## 運用チェックリスト

最後に、同じ種類の事故を短時間で切り分けるためのチェックリストをまとめる。

| 順序 | 確認すること | 成功の証拠 | 失敗時に見る場所 |
| ---: | --- | --- | --- |
| 1 | Mod の初期化 | 対象Modがロード済み | ModTheSpire / ゲームログ |
| 2 | 設定の実読込先 | Mod固有の設定に有効な `command` | 実装・生成済み設定ファイル |
| 3 | 外部プロセス生成 | Pythonプロセスとボット起動ログ | プロセス一覧・stderr・ボットログ |
| 4 | ハンドシェイク | `ready` と状態応答 | Communication Mod ログ |
| 5 | コマンド拒否 | エラー理由がそのまま記録される | 構造化イベントログ |
| 6 | ロケール | IDと表示名を別管理できる | 英日などの統合テスト |
| 7 | 戦略評価 | 固定seed群の集計値 | 実行結果のCSV・可視化 |

## おわりに

自動操作ボットの障害は、意思決定アルゴリズムだけでは起きない。設定ファイルの名前空間、ローカライズされた表示名、エラー応答の型、テストの import 解決といった周辺の契約が崩れれば、どれほど良いAIでも動作を観測できなくなる。

今回の記録から得た最も実用的な原則は、**表示名ではなく安定IDで通信し、正常応答とエラー応答を最初に分岐し、プロセス生成からゲーム内適用までの各段階を別々にログで証明する**ことである。そうして初めて、「ボットは弱いのか」「ボットはそもそも正しくゲームを見ているのか」を同じ実験の中で混同せずに済む。
